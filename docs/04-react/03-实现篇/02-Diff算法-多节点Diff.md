# 多节点 Diff：5v5 团战换人与跳刀乱序抓包对决

> 战场格局: 5v5 大兵团正面交锋（同级存在多个子节点数组）  
> 核心战法: 为什么不支持双指针？两轮冲锋大排查与 lastPlacedIndex 越位抓包！

---

在上一回的 Solo 单挑中，我们搞懂了单节点的生死安检。
但峡谷里绝大多数战况都是 **5v5 团战、多兵种混合推进**（比如 `<ul > <li key="0">0</li> <li key="1">1</li> ... </ul>`）。

当返回的 JSX 是一个数组时，同级多节点的 **Diff 算法大决战** 正式打响！

---

## 🚷 一、战术疑云：为什么不能用“双指针”首尾夹击？

刷过 LeetCode 算法题的选手都知道，面对两个数组找不同，最强套路是 **双指针（Two Pointers）**：头指针、尾指针同时往中间挤，速度极快（Vue 2 和 Vue 3 就是这么干的）。

**为什么 React 偏偏不用双指针？！**
> **因为数据结构被卡死了！**  
> 虽然新英雄列表 `newChildren` 是一个标准的 JS 数组，但站在战场上的老兵部队 `current fiber` 却是一条 **由 `sibling` 指针链接的单向链表**！  
> 单向链表**根本没有从后往前的指针**，你无法在常数时间 $O(1)$ 拿到最后一个老兄弟！强行搞双指针只会把时间复杂度倒退回灾难。

因此，React 独创了符合单向链表特性的战术 —— **【两轮冲锋遍历法】**！
- **第一轮冲锋**：快速检查原地换装的老英雄（处理纯属性更新）；
- **第二轮冲锋**：乱序大抓包、空投新兵与阵亡清除。

---

## 🏃 二、第一轮冲锋：快速对线检查（只抓常规换装）

冲锋步骤如下：
1. `let i = 0`，同时排查 `newChildren[0]` 和 `oldFiber`；
2. 如果 `key` 和 `type` 完全一样，说明是同一个英雄换了身装备，**直接复用！`i++`，老兵指针指向 `oldFiber.sibling`**；
3. **🚨 关键跳出条件**：
   - 一旦遇到某个位置 `key` 对不上，**立刻打断施法，第一轮冲锋瞬间结束！**
   - 此时战场陷入僵局：后面的英雄顺序很可能全乱了！

---

## 🌪️ 三、第二轮冲锋：四大残局与 Map 闪电战

第一轮冲锋结束后，战场会呈现以下四种残局之一：

### 战况 1：新老英雄同时检查完毕
最完美的平稳局，所有人原地换装，Diff 直接胜利鸣金收兵！

### 战况 2：老兵看完了，新兵还有剩余（新英雄空投）
老阵容全复用完了，新队伍里还有没上场的小兵：
**直接遍历剩下的小兵，全部贴上 `Placement`（空投入场）标记！**

### 战况 3：新兵看完了，老兵还有剩余（敌方团灭收割）
新队伍已经齐活了，老阵营里还有多余的老兵：
**遍历剩下的老兵，全部贴上 `Deletion`（击杀拔除）标记！**

### 战况 4：新老部队都没看完（乱序团战大洗牌，核心精髓！）
这说明有英雄**换位插队、乱序走位**了！

#### 第一步：把老兵全部关进军营速查字典（Map）
为了在 $O(1)$ 速度找到老兵，React 将所有还没退场的老兵塞进一个 Map 字典：
```ts
const existingChildren = mapRemainingChildren(returnFiber, oldFiber);
// key -> oldFiber (以身份证为索引，瞬间锁定老英雄肉身)
```

#### 第二步：核心参照标杆 —— `lastPlacedIndex`（越位抓包指针）
这是整个 React 源码中最精妙的一行设计：**如何判定一个英雄是否在屏幕上移动了真实位置？**

React 立下了一根标杆：**`lastPlacedIndex`**（记录在老阵营中出现过的最靠右的位置，初始为 `0`）。
我们从左到右遍历新队伍：
- 拿到新英雄的 `key`，去 Map 字典里查出他在老阵营中的原始站位 `oldIndex`；
- **如果 `oldIndex >= lastPlacedIndex`**：
  > 说明这个英雄在老阵营里本来就站在右边，现在新队伍里他依然相对靠右！  
  > **判定：他不需要移动！** 并把标杆刷新为他的老位置：`lastPlacedIndex = oldIndex`；
- **如果 `oldIndex < lastPlacedIndex`**：
  > **🚨 越位抓包！**  
  > 标杆已经推到了第 3 位，你这个英雄在老阵营里明明站在第 1 位（左边），现在在新队伍里却排在标杆的右边！  
  > 说明你跨过了前面的战友向前超车了！  
  > **判定：打上 `Placement` 标记，必须在真实 DOM 屏幕上拔出并向右移动！**

## 🎮 四、峡谷实战模拟推演（血泪教训）

看下面这两个经典战局，彻底颠覆你的直觉：

### 实战对局 1：
- 老阵营：`a, b, c, d`
- 新阵营：`a, c, d, b`

1. **第一轮**：`a` 对 `a`，复用！标杆 `lastPlacedIndex = 0`。下一位 `c` 对 `b`，key 不匹配，第一轮立刻跳出！
2. **第二轮**：剩余老兵 `[b, c, d]` 存入 Map。
3. 检查新英雄 `c`：老索引是 `2`。$2 \ge 0$，**c 不动**，标杆刷新为 `lastPlacedIndex = 2`；
4. 检查新英雄 `d`：老索引是 `3`。$3 \ge 2$，**d 不动**，标杆刷新为 `lastPlacedIndex = 3`；
5. 检查新英雄 `b`：老索引是 `1`。$1 < 3$ **（越位被抓！）**，**b 被标记移动！**
6. **战果**：`a, c, d` 纹丝不动，只有 `b` 英雄瞬移到了最后。DOM 操作代价极小！

### 实战对局 2（反直觉灾难）：
- 老阵营：`a, b, c, d`
- 新阵营：`d, a, b, c`

按照正常人的直觉：“这不就是把最后一个英雄 `d` 提到最前面吗？移动一次 `d` 不就搞定了？”
**看看 React 的真实判定流程：**

1. 第一轮比对：`d` 对 `a`，key 不匹配，第一轮立刻跳出！
2. 剩余老兵全部进 Map。
3. 检查新英雄 `d`：老索引是 `3`。$3 \ge 0$，**d 不动！** 标杆刷新为 `lastPlacedIndex = 3`！
4. 检查新英雄 `a`：老索引是 `0`。$0 < 3$，**a 判定越位，移动！**
5. 检查新英雄 `b`：老索引是 `1`。$1 < 3$，**b 判定越位，移动！**
6. 检查新英雄 `c`：老索引是 `2`。$2 < 3$，**c 判定越位，移动！**
7. **惨烈战果：React 让 `d` 稳如泰山原地不动，把 `a, b, c` 三个英雄全都拔出来重新插了一遍！移动了 3 次！**

### 💡 顶级电竞选手的架构启示：
在日常写业务列表时，**尽量避免将尾部元素直接移到头部（如无脑 `unshift`）**，这会直接击溃 React 的 `lastPlacedIndex` 判定，引发连环 DOM 移动风暴！

## 🏆 五、本回总结与战术通报

1. **链表约束**：单向 `sibling` 链表决定了无法使用双端指针，必须走两轮冲锋遍历；
2. **第一轮抓更新**：同位比对，一旦 key 错位立即跳出；
3. **第二轮抓越位**：借助 Map 与单调递增的 `lastPlacedIndex` 标杆，小于标杆者全部判定移动。
