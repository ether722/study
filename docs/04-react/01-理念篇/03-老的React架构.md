> 战况回顾: 为什么一代战神 React 15 惨遭推倒重做？  
> 核心病灶: 递归死磕，站桩读条无法位移，稍微中断就当场演戏！

---

在上一回中，我们确立了战队的最高纲领：**【光速响应】**。

而 React 之所以从 v15 惨烈升级到 v16、彻底把地基连根拔起，就是因为 **React 15 的战术体系根本打不了高帧率团战，随时站桩暴毙**。

本回我们来深入复盘：React 15 到底是怎么把自己坑死的？

---

## 🏛️ 一、React 15 的两层编制：参谋部与前线炮台

React 15 的作战架构只有精简的两层编制：

1. **Reconciler（协调器 / 战术参谋部）**：负责侦察对比，找出是哪个英雄/防御塔的状态变了。
2. **Renderer（渲染器 / 宿主前线炮台）**：负责听从参谋部指令，把变动真正打在屏幕上。

```
[玩家按键/指令触发] ──► Reconciler (参谋部对比找不同) ──► Renderer (前线把真实 DOM 揍一遍)
```

### 1. 战术参谋部（Reconciler）的日常工作
当选手按下 `this.setState`、`forceUpdate` 发起团战进攻时，Reconciler 会做以下 4 步：
- 叫出组件的 `render()` 方法，将 JSX 编译成虚拟 DOM（战场兵推沙盘）；
- 将新沙盘和上一帧的老沙盘进行对比（Diff 算法）；
- 圈出本次作战中哪些地方发生了变动；
- 通报前线炮台（Renderer）：“目标已锁定，立刻开火！”

### 2. 跨平台前线炮台（Renderer）
因为 React 支持多端作战，所以配有不同的终结炮台：
- **ReactDOM**：负责在浏览器 PC/移动端网页打阵地战；
- **ReactNative**：空投到 iOS/Android 原生手机端打巷战；
- **ReactTest**：在靶场里打纯 JS 虚拟测试；
- **ReactArt**：在 Canvas/SVG 上画弹道特效。

## ☠️ 二、致命死穴：原地站桩读条递归与撕裂惨剧

在 React 15 的参谋部里，挂载英雄叫 `mountComponent`，升级英雄叫 `updateComponent`。
**这两个核心战术函数，全都是【深度优先的纯递归遍历】！**

### 1. 站桩施法，中途无法取消（递归不可逆）
递归就像按下了**无法自取消的长时间原地读条技能**（比如死灵法师的死神镰刀、马尔扎哈的压制）：
- 一旦大招开出，JavaScript 的调用栈就层层压入；
- 只要组件树嵌套很深，递归执行时间就会一路狂飙突破 16.6ms；
- 在这期间，选手的任何走位点击都被死死锁在事件队列外，英雄站在原地挨打，**画面直接卡死掉帧！**

### 2. 为什么 React 15 不能直接“按 ESC 键打断施法”？
你可能会问：既然递归太慢，那让它中途停一下，走位一下再回来打不行吗？
**不行！一旦打断，页面就会瞬间演变成“假赛车祸现场”！**

看下面这个战场实况 Demo：
- 初始基地有 3 个小兵，数值分别是 `1, 2, 3`。
- 英雄点了技能升级，期望所有小兵数值乘 2，变成 `2, 4, 6`。

在 React 15 架构下：
> **Reconciler 和 Renderer 是【像连珠炮一样同步交替干活】的！**
> 参谋部算完第 1 个小兵，前线炮台就立刻去改真实 DOM；然后再算第 2 个小兵，再去改真实 DOM！

```
算小兵1 ──► 真实DOM变(2,2,3) ──► 算小兵2 ──► 真实DOM变(2,4,3) ──► 算小兵3 ──► 真实DOM变(2,4,6)
```

平时因为执行太快，玩家肉眼觉得是一瞬间完成的。
**但如果中间真的被高优先级走位打断了会发生什么？**

```
算完小兵1并改了真实DOM ──► 【🚨 突然被玩家鼠标点击打断中断！】 ──► 浏览器立刻绘制画面！
```

结果灾难发生了：
> **玩家期望看到 `[2, 4, 6]`，结果屏幕上活生生卡住了一半半成品：`[2, 2, 3]`！**  
> 英雄技能放了一半，血条扣了一半，界面彻底碎裂不一致！

## 💥 三、惨败教训：为什么必须彻底推翻重做？

React 15 之所以无法实现并发中断，核心根源是：
1. **数据结构太脆弱**：纯函数调用栈不可记录进度，无法暂停后恢复现场；
2. **边算边改真实 DOM**：参谋部（计算）和前线（修改真实 DOM）死死绑定在一起，无法在内存中搞“秘密草稿演练”。

**教练组最终裁决：**
为了支持走 A 中断，同时又绝不把半成品画面露给观众，必须把架构升级为三层编制，并引入**双缓存替身镜像系统**！
