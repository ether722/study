## 战场核心世界观：从“点金手炼金”到“泉水清道夫”

在漫长的天梯对局中：
1. **V8 引擎 = 极速出装铸造厂**：
   - 如果每次平 A 都要把源文本重新翻译一遍，团战早就掉帧成幻灯片了。
   - V8 引擎先用 **Ignition 解释器**以最快速度把代码变成字节码运行起来（开局裸装出门）；
   - 一旦侦测到某些函数被疯狂调用（如普通攻击循环），**TurboFan 编译器立即将其升级为极致优化的机器汇编（合出神装极速输出）**！但只要你突然乱改对象形状（隐藏类突变），编译器就会狼狈地触发“**去优化（Deopt）**”退回解释器！
2. **垃圾回收（GC）= 泉水保洁大爷**：
   - 英雄丢在地上的破烂树枝、被斩杀的小兵尸体，如果堆满战场，内存就会被撑爆崩溃（Out of Memory）。
   - 保洁大爷从**根节点（GC Roots，全局对象、当前调用栈变量）**出发，顺着引用线去摸，凡是**摸不到的孤儿对象，一律判定为战损垃圾，直接扫地出门，回收内存空间！**

## 第一战：V8 引擎优化黑魔法——隐藏类（Hidden Classes）与内联缓存（Inline Cache）

### 1.1 为什么不要在对象创建后随意动态乱加属性？
在 C++ / Java 中，对象的内存偏移量是固定的；而 JS 对象是动态哈希表，查属性本来很慢。V8 为了提速，在底层给每个对象绑定了**隐藏类（Hidden Class / Map）**。

```javascript
// ❌ 业余出装：让 V8 隐藏类疯狂突变分裂，性能暴跌！
function createHeroSlow() {
  const hero = {};
  if (Math.random() > 0.5) {
    hero.attack = 100; // 产生隐藏类 Transition C0 -> C1
    hero.defense = 50;  // 产生隐藏类 Transition C1 -> C2
  } else {
    hero.defense = 50;  // 产生不同分支的隐藏类 C0 -> C3
    hero.attack = 100; // 产生 C3 -> C4
  }
  return hero;
}

// ✅ 职业战队出装：严格保持属性初始化顺序一致，共享同一个隐藏类！
class ProHero {
  constructor(attack, defense) {
    this.attack = attack;   // 固定的隐藏类演进路线
    this.defense = defense; // TurboFan 直接通过内联缓存（Inline Cache）毫秒级直读！
  }
}
```

## 第二战：内存分配模型——调用栈（Stack）vs 内存堆（Heap）

- **栈内存（Stack）**：
  - **存放内容**：基本原始类型（Number, Boolean, String, Symbol 等）和指向对象的**引用地址指针**。
  - **特点**：连续内存空间，后进先出，由系统自动极速分配和弹出，开销接近于 0。
- **堆内存（Heap）**：
  - **存放内容**：大小不固定、生命周期复杂的引用对象（Object, Array, Function, Map 等）。
  - **特点**：动态树状/图状散列分布，容易产生碎片，必须依赖 **垃圾回收器（Garbage Collector）** 定期巡检清理。

## 第三战：垃圾回收 GC 进化史——从“引用计数”到“V8 分代回收”

### 3.1 远古时代：引用计数（Reference Counting）与循环引用自爆
- **原理**：对象身上挂一个计数器，有人引用它就 +1，取消引用就 -1。计数器为 0 就回收。
- **致命命门：互相给技能打配合（循环引用）导致永久内存泄漏！**

```javascript
function catastrophicLeak() {
  const heroA = {};
  const heroB = {};
  heroA.partner = heroB; // heroB 引用计数 = 1
  heroB.partner = heroA; // heroA 引用计数 = 1
  // 函数执行完毕，heroA 和 heroB 已经无法被外界任何人访问，
  // 但它们的计数器永远都是 1，引用计数算法永远无法清理它们！直接爆内存！
}
```

### 3.2 现代标准：可达性分析（Reachability Analysis / 标记清除）
- **核心算法**：从一组 **GC Roots**（全局变量、活动执行栈顶的局部变量等）出发，沿着对象引用边向下遍历。
  - 能遍历到的对象打上标记：**“存活战力”**；
  - 无法从根节点顺藤摸瓜触达的对象，哪怕它们之间互相引用得再紧密，也全部被判定为**“不可达失联孤儿”**，统统清除！

### 3.3 V8 分代回收机制（Generational Garbage Collection）

V8 依据经验法则**“弱代假说（The Weak Generational Hypothesis）”**：**绝大多数对象的寿命极其短暂（如临时变量、帧内数据），而熬过多次筛选的对象往往会长久存活**。

因此 V8 把堆内存划分为两大核心战区：

```
┌────────────────────────────────────────────────────────────────────────┐
│                        V8 内存堆分代空间分布                            │
└────────────────────────────────────────────────────────────────────────┘

 【新生代空间 (New Space, 32MB~64MB)】          【老生代空间 (Old Space, >1.4GB)】
 ┌──────────────────────────────────┐          ┌───────────────────────────┐
 │ 使用 Scavenge 算法 (极速复制)     │          │ 使用 标记-清除 / 标记-整理  │
 │                                  │ 经过 2 次 │                           │
 │  [From 空间] ──> [To 空间]        │ GC 仍存活 │  [存活长驻对象 / 大对象]   │
 │  (存活对象复制过去，清空 From)     │ ────────>│  (定期压缩整理内存碎片)    │
 └──────────────────────────────────┘ 晋升机制  └───────────────────────────┘
```

1. **新生代（Scavenge 复制算法，Cheney 算法）**：
   - 内存平分为两半：`From` 空间与 `To` 空间。
   - 活跃对象从 `From` 极速复制到 `To`（连续存放无碎片），然后两空间身份对调！速度极快（几十毫秒内搞定）。
   - **晋升机制（Promotion）**：如果在一次 Scavenge 后对象依然存活，或者 `To` 空间占用超过 25%，该对象晋升到老生代！
2. **老生代（Mark-Sweep 标记清除 & Mark-Compact 标记整理）**：
   - **增量标记（Incremental Marking）**：将原本长达数百毫秒的全局暂停（Stop-The-World 全停顿）切碎成多段微小切片，穿插在 JS 主线程执行缝隙中，彻底消灭掉帧卡顿！
   - **并发与并行 GC**：利用后台多个 Worker 线程协同标记与清理，主线程几乎感受不到后勤压力。

## 第四战：防泄漏神装——WeakMap 与 WeakSet 的幽灵指针

在开发大型复杂应用时，给 DOM 节点挂载数据或做私有属性缓存，最容易因为忘记手动 `delete` 导致整个 DOM 树无法被 GC 回收（游离 DOM 内存泄漏）。

### 4.1 WeakMap 的弱引用超能力
- **键名必须是对象**。
- **弱引用（Weak Reference）**：`WeakMap` 对键名对象的引用**不计入垃圾回收可达性考量**！
- 如果没有外界其他强引用抓着这个键名对象，**GC 降临时会直接将其销毁，WeakMap 内部对应的键值对自动随风蒸发！**

```javascript
// 实战：给防御塔 DOM 绑定实时作战数据，绝不泄漏内存！
const towerMetadata = new WeakMap();

let towerElement = document.getElementById('dire-tier1-tower');
towerMetadata.set(towerElement, { armor: 20, lastHitHero: 'Juggernaut' });

// 当防御塔被敌方推平，从 DOM 树中被移除：
towerElement.parentNode.removeChild(towerElement);
towerElement = null; // 切断外部唯一强引用！

// 结果：下一次 GC 时，towerElement 占用的内存被彻底回收，
// towerMetadata 里的映射项自动消失，完全不需要手动 cleanUp()！
```

## 第五战：底核二进制内存直通——ArrayBuffer 与 TypedArray

当涉及音视频、WebGL 渲染、或 WebSocket 大规模二进制流时，常规 JS 对象的动态开销无法承受。此时需要动用**底层连续内存块操作神器**：

```javascript
// 1. 在堆内存中开辟一块纯粹的 16 字节连续二进制物理缓冲区
const buffer = new ArrayBuffer(16);

// 2. 用类型化数组视图 (TypedArray) 像操作 C 语言指针一样操作内存
// 创建 32 位整型视图 (每个数字占 4 字节，共能存 16 / 4 = 4 个数值)
const int32View = new Int32Array(buffer);
int32View[0] = 9999;
int32View[1] = 8888;

// 3. 同时可以用浮点视图读取同一块内存，实现零拷贝数据转译！
const float32View = new Float32Array(buffer);
console.log("同一物理内存的整型值:", int32View[0]);
console.log("同一物理内存的浮点解释:", float32View[0]);
```
